# PR 생성

본문 형식의 기준은 `.github/PULL_REQUEST_TEMPLATE.md`입니다. 섹션과 주석 안내는 템플릿을 따르고, 이 스킬은 템플릿에 없는 절차만 정합니다. 기준 브랜치는 따로 지정이 없으면 `main`입니다.

## 1. 전제 점검

다음 중 하나라도 어긋나면 멈추고 알립니다.

- 현재 브랜치가 기준 브랜치가 아닙니다.
- 커밋하지 않은 변경이 없습니다(`git status --short`).
- 기준 브랜치보다 앞선 커밋이 있습니다(`git log origin/<base>..HEAD`).
- 이 브랜치로 열린 PR이 없습니다(`gh pr list --head <branch>`).

## 2. 제목

`commit` 스킬과 같은 형식입니다. 커밋이 하나면 그 메시지를 그대로, 여럿이면 전체를 대표하는 한 줄로 씁니다.

## 3. 본문

템플릿을 읽고 모든 섹션을 한국어로 채웁니다. 섹션을 지우거나 추가하지 않고, 해당 없으면 "없음"이라고 씁니다. HTML 주석은 지웁니다.

**추상화 수준**: 리뷰어가 diff를 열지 않고 본문만으로 이해하는 것이 목표입니다. 기능·동작·개념으로 씁니다. 파일 경로, 클래스·함수 이름, 줄 수, 필드 이름은 후속 작업에서만 씁니다.

- **의도**: 대화나 이슈에서 드러난 목적을 씁니다. diff만으로 의도를 알 수 없으면 추측하지 말고 사용자에게 묻습니다.
- **변경 사항**: 사용자나 시스템이 겪는 변화 하나당 한 항목, `전 → 후`로 씁니다. 레이어나 파일별로 나누지 않습니다.
- **주요 결정**: 대안이 있었던 판단만 `결정 — 이유 (버린 대안)` 한 줄로 씁니다.
- **계약·설정 변경**: 새로 생기거나 바뀌는 API·데이터·설정·의존성과 영향받는 쪽을 씁니다. `api-contract` 스킬로 상대 영역과 맞는지 확인한 결과를 반영합니다.
- **범위 밖**: 대화에서 일부러 빼기로 한 것과 다른 PR에 의존하는 것을 씁니다.
- **검증**: 실제로 확인한 것과 결과만 씁니다. 하지 않은 것을 통과했다고 쓰지 않습니다. CI의 테스트·빌드 결과는 반복하지 않습니다.
- **후속 작업**: diff와 의도를 보고 남은 일을 제안합니다.
  - 볼 것: 설정해야 할 시크릿·변수·라벨, 배포 절차 변화, 상대 영역에서 맞출 것, 범위 밖으로 미룬 일, 첫 실행으로만 확인 가능한 가정.
  - 각 항목은 `- [ ]` 한 줄로, 바로 실행할 수 있게 경로나 명령까지 씁니다. 머지 전에 필요하면 `(머지 전)`을 붙입니다.
  - 제안을 PR에 올리기 전에 사용자에게 보여 확인받습니다. CI처럼 물을 수 없으면 그대로 올리고 "AI 제안" 항목임을 알립니다.
- 관련 이슈가 있으면 `close #N`을 마지막 줄에 둡니다.
- Claude 작성 표시나 "Generated with" 줄은 넣지 않습니다.

**자체 점검**: 올리기 전에 본문만 보고 다음에 답할 수 있는지 확인합니다. 답할 수 없는 질문이 있으면 해당 섹션을 보완합니다.

1. 머지되면 무엇이 가능해지는가
2. 사용자·시스템 동작이 어떻게 바뀌는가
3. 어떤 판단을 왜 내렸는가
4. 다른 영역이나 운영 설정에 무엇이 영향을 주는가
5. 무엇을 일부러 하지 않았는가
6. 무엇이 실제로 확인됐는가
7. 무엇이 남았는가

## 4. 푸시와 생성

1. PR 대상 저장소를 가리키는 원격으로 푸시합니다: `git push -u <remote> HEAD`. 원격이 여럿이면 `git remote -v`로 확인합니다.
2. 원격과 갈라졌으면 멈추고 물어봅니다. 자동 rebase나 force push는 하지 않습니다.
3. `gh pr create --base <base> --title "<제목>" --body-file <파일>`로 만들고(초안이면 `--draft`), PR 번호와 URL을 알립니다.
